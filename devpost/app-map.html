AccessDiff · Code reference

From a removal test to its evidence

AccessDiff compares effective read access in two supplied snapshots. An optional, complete business reference identifies access that is not required and required access that is missing. A temporary single-removal scenario shows what would change before any real permission is edited.

Validated inputs

Before and After JSON describe people, groups and resources. The optional reference explicitly declares needs across the complete After scope.

Deterministic calculations

The graph engine computes reachable access. Reference comparison and a copy with one relation removed produce distinct findings.

Current evidence

The page session owns input and result freshness. The interface explains findings; a downloaded HTML report preserves the current evidence.

Model: positive read grants to flat resources, directly or through nested groups. Imported data stays in browser page memory; a reload clears it. No runtime AI, external API or persistent application storage. A downloaded report remains a separate local file.

A practice to reuse

Make a requirement observable, then protect it with a test. A removed relationship does not necessarily mean lost access: another route may still grant the same right. A concrete example makes that distinction checkable.

The technical specification, under Components → Single-Relationship Removal Simulation, requires a valid surviving route for affected retained access. The test removing a direct grant preserves other rights and reports a retained indirect route in tests/simulation.test.js removes a direct person → resource grant and expects zero losses, one affected retained pair, and a surviving person → group → resource path.

For another project, write the expected observable difference first, including what must stay unchanged. Link that criterion to a small example, the code that enforces it, and a browser check of the same behavior.

Related evidence: successive removals never accumulate

The specification’s Import Session and Freshness section requires every test to start from unchanged After. tests/session.test.js checks this with a second simulation removes only its selected relation from original After, never the first removal: removing the second of two direct grants produces exactly one loss for the second resource and leaves After unchanged. In src/access.js, computeAccess supplies the effective-access calculation used by both scenarios.

To change this, start here

Scenario wording or layout
src/app.js → renderSimulation and renderSimulationDetail; styles.css controls visual styles. Keep the original comparison and scenario labels distinct.
Accepted input format
src/snapshot.js → parseSnapshot / validateSnapshot. Update the matching contract in docs/input-format.md when changing supported data.
Access or business-need calculations
src/access.js → computeAccess; src/policy.js → evaluateReference. Access reachability and declared necessity are separate decisions; verify both with existing tests.
Downloaded report content
src/report.js → createReport; tests/report.test.js checks evidence and escaping. The report must reflect the current session result and distinguish its two comparisons.

Run the app again

From the repository root, with Node.js 24 installed:

npm start

Open http://127.0.0.1:5174/. Keep its terminal open; stop it with Ctrl+C. No package installation is required. The app uses local HTTP for its modules and examples.
